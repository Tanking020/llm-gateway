## 4. 上游 HTTP client 用「应用级共享」而不是「每请求新建」

| 项 | 内容 |
|---|---|
| **背景** | 每个请求都要调上游 LLM。client 什么时候创建、什么时候关闭？ |

## 6. 上游错误分三层翻译（L1 / L2 / L3）

| 项 | 内容 |
|---|---|
| **背景** | 调上游 LLM 时，失败有非常多形态：连不上、返回 4xx、返回 200 但 body 是 HTML、body 是空、字段改名、`{"error":...}`… |
| **方案对比** | A 每个调用点各自 `try/except`<br>B 只在最外层统一捕获<br>**C 分三层，全部翻译成 `AppError`** |
| **决定** | **C**。三层定义：<br>**L1** 上游根本没回应（DNS / TCP / TLS / 超时）→ `UPSTREAM_UNREACHABLE`<br>**L2** 有回应但状态码非 2xx → `UPSTREAM_BAD_STATUS`<br>**L3** 回了 200 但 body 结构不合规 → `UPSTREAM_MALFORMED`<br>三者都映射到 **502**（不是 500，因为不是我们的错） |
| **代价** ⚠️ | ⚠️ **路由层不许 `import httpx`** —— 用 `ruff` 的 `TID251`（banned-api）机械保证。这限制了"临时在路由里直接调上游"这种快速写法 |
| **重审条件** | 接入第二家上游、且错误语义不同时 → 需要抽象出 provider 接口 |

> 📍 原始位置：[阶段1-FastAPI速成.md](阶段1-FastAPI速成.md) §9 系列；[学习档案与路线图.md](学习档案与路线图.md) 待办 #19（已解决）

## 7. 流式接口用 SSE，而不是 WebSocket 或轮询

| 项 | 内容 |
|---|---|
| **背景** | 聊天回答是"一个字一个字出来"的，需要把过程实时推给前端 |
| **方案对比** | **A SSE**（`text/event-stream`）：基于普通 HTTP，单向服务器→客户端<br>B WebSocket：双向，但需要协议升级、连接管理、心跳<br>C 轮询：客户端每隔 1 秒问一次"好了吗" |
| **决定** | **A**。理由：① 需求是**单向**（回答只需要下发）；② SSE 走普通 HTTP，能和现有中间件 / 鉴权 / 日志复用；③ 浏览器有原生 `EventSource` |
| **代价** ⚠️ | ① **不能中途"回传"**（用户想在上游生成时打断，只能靠断开连接）；② 一旦响应头发出，**状态码就改不了了** —— 所以错误必须在**流开始前**（pre-flight）发现，或编码进流内 |
| **重审条件** | 需要"用户边说边发、模型边听边答"（语音对话）→ 换 WebSocket |

> 📍 原始位置：[阶段1-FastAPI速成.md](阶段1-FastAPI速成.md) §9.1~§9.11（整章）

## 9. 请求级数据库会话由依赖统一提交

| 项 | 内容 |
|---|---|
| **背景** | 每个请求可能要多次读写数据库。事务边界应该在哪？ |
| **方案对比** | A 每个路由自己 `await db.commit()`<br>**B `get_db` 依赖统一 commit / rollback** |
| **决定** | **B**。路由里只 `db.add()` / `await db.flush()`，不写 `commit()` |
| **代价** ⚠️ | ① 路由**不能提前提交**（想在中间提交一次、后面还能回滚，做不到）；② 需要 `flush()` 才能拿到自增 id<br>③ ⚠️ **`CancelledError`（客户端断开）会绕过 `except Exception`** → 依赖走 commit 路径，可能提交半截数据。流式接口必须自己守 `except BaseException`（见 [16](#计费记录不能跟着对话一起删) 的相关说明） |
| **重审条件** | 需要"一个请求内多个独立事务"时 → 引入 `async with session.begin()` 分段 |

> 📍 原始位置：[阶段1-FastAPI速成.md](阶段1-FastAPI速成.md) §10.4；[src/app/api/deps.py](../src/app/api/deps.py) 的 `get_db`

## 10. 契约按用途分家（In / Patch / Out）

## 11. 对话标题的长度规则抽成公共类型

| 项 | 内容 |
|---|---|
| **背景** | 创建和更新都要校验标题：非空、≤100 字符、**不能是纯空格** |
| **方案对比** | A 两个模型各写一遍 `Field(min_length=1, max_length=100)`<br>**B 抽出 `ConversationTitle` 类型，两处共用** |
| **决定** | **B**：`Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=100)]` |
| **代价** ⚠️ | ① 类型定义和字段定义分开了，读代码要多跳一次；② 必须用 `StringConstraints` 而不是 `field_validator` —— 📎 实测 `Field(min_length)` 在 `field_validator` **之前**执行，会先按含空格的长度判超长 |
| **重审条件** | 如果将来标题规则和别的字段规则分化 → 拆开 |
| 📎 **起因** | 测试中发现 `{"title": "   "}` 返回 **200** 并把 3 个空格存进了库（前端显示空白标题） |

> 📍 原始位置：[阶段1-FastAPI速成.md](阶段1-FastAPI速成.md) §10.5、§10.5f

## 12. PATCH 而不是 PUT，且空 body 直接拒绝

| 项 | 内容 |
|---|---|
| **背景** | 更新对话标题，该用什么方法？空 body 怎么办？ |
| **方案对比（方法）** | A `PUT`（整体替换）<br>**B `PATCH`（部分更新）** |
| **方案对比（空 body）** | A 宽容：`{}` 当 no-op，返回 200（RFC 7396 允许）<br>**B 严格：`{}` 返回 422** |
| **决定** | **B + B** |
| **代价** ⚠️ | ① 现在只有一个可改字段，`PATCH` 和 `PUT` **行为完全一样** —— 选 `PATCH` 是为将来加字段留余地；② 严格拒绝 `{}` 意味着**多字段 PATCH 时必须用 `model_dump(exclude_unset=True)`**，否则分不清"没传"和"传了 null" |
| **重审条件** | 字段多到需要"客户端只传变化项"时 → 必须换成 `exclude_unset` 写法 |
| 📎 **为什么严格更好** | ⭐ **「必填字段」是免费的 bug 探测器**：前端把 `title` 拼成 `titel` 时，`title: str`（必填）会报 422 立刻暴露；改成"可选 + 默认 None"就变成 **200 但一个字没改**（静默成功） |

> 📍 原始位置：[阶段1-FastAPI速成.md](阶段1-FastAPI速成.md) §10.5「PATCH」小节

## 13. 数据库用 SQLite 起步，PostgreSQL 留作切换目标

| 项 | 内容 |
|---|---|
| **背景** | 学习项目用什么数据库？ |
| **方案对比** | **A SQLite**：零安装、文件即数据库、`aiosqlite` 异步驱动<br>B PostgreSQL：生产级，但要装服务 / Docker |
| **决定** | **A**，但**所有代码按"将来能切 PostgreSQL"写**：用 SQLAlchemy ORM（不写方言 SQL）、`database_url` 从配置读、`ForeignKey` / 长度限制都按 PostgreSQL 语义声明 |
| **代价** ⚠️ | SQLite 有**三个方言差异**必须记住：<br>① **不强制 `String(100)`** —— 实测塞 200 字符能存进去，长度校验只能靠 pydantic<br>② **默认不强制外键** —— 必须挂 `connect` 事件执行 `PRAGMA foreign_keys=ON`<br>③ **不存时区** —— `DateTime(timezone=True)` 也丢 `tzinfo`，存 UTC 读回来是 `naive` |
| **重审条件** | 需要并发写 / 全文检索 / JSON 查询 → 切 PostgreSQL（改 `database_url` + 装 `asyncpg`） |

| **背景** | `create_async_engine()` 持有连接池。在哪创建？ |
| **方案对比** | A 每请求新建（连接池毫无意义）<br>B 放在 `lifespan` 里，挂 `app.state`<br>**C 模块级单例** |
| **决定** | **C**（引擎 + `SessionMaker` 都是模块级），**但释放放在 `lifespan` 的关闭段** `await engine.dispose()` |
| **代价** ⚠️ | ① 模块级 = **import 时创建**，测试时不好替换（要靠 `dependency_overrides` 或改 `DATABASE_URL` 环境变量）；② `dispose()` 必须记得写，否则连接泄漏 |
| **重审条件** | 需要多租户 / 多库时 → 改成工厂函数 + `app.state` 字典 |
| 📎 **为什么不选 B** | 四条理由见笔记 §10.3：① `deps.py` 要 import 它，lifespan 里创建时序太晚；② mypy 拿不到类型；③ 测试替换更麻烦；④ 引擎本身不是"请求级资源" |

## 16. 计费记录不能跟着对话一起删

| 项 | 内容 |
|---|---|
| **背景** | `llm_calls`（每次 LLM 调用的 token 用量）是 `conversations` 的子表。删对话时，计费记录怎么办？ |
| **方案对比** | A `cascade="all, delete-orphan"` + `ondelete="CASCADE"`：一起删<br>**B 去掉 `cascade` + `ondelete="SET NULL"`**：只断关联，记录保留<br>C 去掉外键，`conversation_id` 当历史事实保留<br>D 软删除（`deleted_at`）：父行也不真删 |
| **决定** | **B** |
| **代价** ⚠️ | **丢失「这笔钱是哪个已删对话花的」**。📎 实测删 1 个对话后，3 条记录变成 `conversation_id = NULL` |
| **重审条件** | ① 需要"已删对话的费用明细"→ 改 D（软删除）或 C<br>② 需要按对话维度做账单报表 → 必须提前改，否则历史数据无法追溯 |
| 📎 **为什么不能选 A** | 📎 实测：2 个对话各 3 条计费（各 900 token），删掉「对话A」后<br>合计从 **1800 → 900 token** —— **「本月一共花了多少」这个账从此算错** |
| ⭐⭐ **判据（这条是本决策的核心）** | **「子记录该不该跟着父记录消失」取决于「谁有权删父记录」。<br>用户能删的东西，它下面不能挂不可再生的记录。** |
| ⭐ 补充 | `LlmCall` 本身是**自足**的（`model` / 三种 token / `created_at` 都不依赖父表），只有「归属哪个对话」依赖父表 —— 所以断关联只丢这一项，**账本身还在** |

> 📍 原始位置：[src/app/models.py](../src/app/models.py) 的 `Conversation.calls` 与 `LlmCall.conversation_id`
> ⚠️ 相关知识：`ondelete` 与 `cascade` 的两层分工、10 组矩阵实测 → [阶段1-FastAPI速成.md](阶段1-FastAPI速成.md) §10.6a
