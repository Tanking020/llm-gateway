## 一、结论

**代码质量在同类项目这一档里靠前；生产就绪度 2026-11-17 重推为 L3−。**

Step 13 已经补掉了原评审里最要命的一半：**谁都不能白用**（鉴权 + 租户隔离 + 越权 404）与 **发版不断在途回答**（优雅停机 + 验收脚本），
以及「201 等于已提交」「500 读不到 request_id」「慢速滴答拖死请求」这三类静默故障。

仍差的是**三件「没发生过的事」**：

1. ~~**没有部署产物**~~ ✅ **2026-11-19 已解决** —— 镜像 + 一次性迁移 + nginx 入口都真跑过（13a / 决策 43~46）；剩「灰度与回滚」一条（#49 收尾项）
2. ~~不知道能扛多少~~ —— ✅ **2026-11-20 已有实测数字**（13f / 决策 51）：`c=4` 首帧 p50 **47ms** 全 200、`c=16` 起 **503**、`db_pool_checked_out` 峰值**始终 4**（= 闸门值，池上限 15 → 池不是瓶颈）。⚠️ 仅单进程 + SQLite，多副本 / PostgreSQL 需重测
3. ~~出事只能人工翻日志~~ —— ✅ **2026-11-20 已补**：访问日志带客户端 IP（决策 47）、一行一 JSON + Docker 侧轮转（决策 48）、5 个指标 + 3 条告警规则（决策 50）。⚠️ **告警无接收端**（未部署 Prometheus/Alertmanager），目前只能手工抓 `/metrics`

> 一句话判据：**生产级的定义是「被 1000 个人同时打」和「线上出事后 3 分钟内定位」这两件事的频率与代价。**
> 第一件事现在有了拦截器但没有数字；第二件事仍然只能靠 `Select-String`。

## 三、排期：什么时候做什么

> 排序原则：**先补能拦住故障的，再补功能的。**
> 依据：故障拦截项每推迟一个阶段，返工面积按「表数量 × 端点数」增长。
>
> ⚠️ **档期以本表为准**：roadmap 待办表里 2026-11-01 之前写的「建议处理时机」可能更保守
> （#36 / #37 / #44 / #55 / #57 原写「阶段 3 部署前」，本次按上线评审**提前到 `P1`**）。

| 档位 | 触发条件（什么时候**必须**做完） | 包含 |
|---|---|---|
| **`P0` 现在** | **Step 12 开工前后**（测试与容量天花板） | 测试地基 / 连接不独占 / 并发与 `max_tokens` 上限 / 上游 429 与 4xx 语义 |
| **`P1` 阶段 1 收口** | **Step 13 部署前**（第一次发版之前） | 鉴权 + `owner_id` / 限流 + body 上限 / Docker + Alembic + 优雅停机 / 指标 + IP + 结构化日志 / CORS 500 / `commit` 时机 / CI |
| **`P2` 公开上线前** | **阶段 4 部署公开网页之前**（第一次有真实外部用户） | 告警阈值 + SLO / 灰度回滚 / PostgreSQL + 备份 + 保留策略 + PII / 幂等与成本刹车<br>（**压测已于 2026-11-14 上调为 `P1`**，见门 3 与 [#76](todos.md)） |

### 为什么是这个顺序

| 顺序 | 理由 |
|---|---|
| 测试先于一切 | 没有回归保护时，改连接生命周期 / 加上限这类「动地基」的改动本身就会引入新 bug，且没人守 |
| 容量先于功能 | #59 让**真实并发上限 ≈ 15**，与买多少上游配额无关。不修，后面所有「能扛多少」的讨论都没有意义 |
| 鉴权先于 RAG/Agent | `owner_id` 的成本 = 表数量 × 端点数。**现在只有 1 张业务表、5 个端点，是最便宜的时刻**（阶段 3 加知识库、阶段 4 加 Agent 会话历史后会翻倍） |
| 观测先于公开流量 | 没有指标告警，第一次真实流量就是「盲飞」：你不知道是好的还是正在坏，只能等用户告诉你 |

### ⛔ 不要做的事

- **不要把 RAG / Agent 排在 `P0` + `P1` 之前**。功能会盖住上面这些坑，而且让它们的修复成本翻倍。
- **不要用「现在只有我一个人用」当理由跳档**。项目定位是产品（规范 §7.0c）；且 #59 这类问题在单机自测时**永远看不见**。

## 五、已经具备的（已经具备的能力）

> 这一节是给评审用的：这些在同类项目这一档里**稀缺**，要主动讲，不要等评审者发现。

| 已有的能力 | 为什么稀缺 |
|---|---|
| `StreamingResponse` **之前**做 pre-flight（先探上游状态码再决定回什么） | 多数人不知道「响应头一发出，状态码就改不了」，会写出「日志 200、实际失败」的服务 |
| 零内容保护 + 异常路径也发 `[DONE]` + `except BaseException` 区分取消 | SSE 的三条退出路径全覆盖，是踩过坑才写得出来的 |
| 账单 `pending/completed/aborted` + `ondelete="SET NULL"` 不删账 | 有「钱」的意识。做 LLM 应用，计费不是附属功能 |
| 📎 客户端断开时账单**确实保住了**（实测 `(1,'aborted')` 落库）—— 我作为审查者原本判断会丢，实测打脸 | 说明 Starlette 断开是「关 body 迭代器」而非「取消整个请求」，依赖收尾照常执行 |
| 游标分页而非 offset（且有「翻页期间删数据会漏一条」的实测） | 工程品味，不是背来的 |
| liveness / readiness 拆开，且拒绝把探库塞进 liveness | 懂 K8s 的失败模式：重启治不好数据库 |
| dev 关 `/docs` 三个端点、prod 与 `DEBUG=true` 组合启动即失败 | 「配置写错要崩，不要静默降级」 |
| 用 ruff banned-api 禁止别处 `import httpx` | **用工具强制架构，而不是靠自觉** —— 很多人做不到 |
| 每条结论都带实测证据、台账写得比多数人的设计文档清楚 | 这是「能长多快」的信号 |

**评审时最掉分的答法**是硬说「这是生产级」。**最加分的答法**是：
「它现在是内部服务级别，距对外服务的差距在这五点上（鉴权 / 限流 / 测试 / 部署 / 观测），原因是 X，下一步是 Y。」
—— 能把差距说得比评审者还清楚，本身就是高级工程师的信号。
