> **一句话**：压测结论只在「其余变量固定」时成立 —— 所以表单必须先记录**前置条件**，
> 再记录数字，最后写**判定**。只抄一张数字表，三个月后没人能解释它为什么是那个数。

## 1. 前置条件（一次压测一套；**任何一项变了都要新开一节**）

| 项 | 本次填写 | 为什么必须记 |
|---|---|---|
| 日期 | | 代码与依赖都会变 |
| 提交 | | 同上；写 `git rev-parse --short HEAD` |
| 机器（CPU / 内存 / OS） | | 单机结论**不能**外推到别的机器 |
| 部署形态 | 单进程 / N 副本 / docker compose | 📎 闸门是**进程级**的 → 2 副本 = 2×槽位 |
| `MAX_CONCURRENT_UPSTREAM_CALLS`（闸门 slots） | | 吞吐上限 = `slots ÷ 单请求服务时长` |
| `UPSTREAM_QUEUE_TIMEOUT` | | 决定「排队」还是「拒绝」 |
| 上游 | 假上游（帧数 × 帧间隔）/ 真上游（哪个模型） | 📎 **服务时长决定一切**，换上游整张表作废 |
| `RATE_LIMIT_PER_MINUTE` / `RATE_LIMIT_BURST` | | 📎 不放大会测到**限流器**而不是容量 |
| 数据库 | SQLite 文件 / PostgreSQL | SQLite 只允许一个写者，池行为完全不同 |
| 探针参数 | `--concurrency` / `--rounds` / `--gate` | 轮数太少，p95 没有意义 |

**每列在回答什么问题**（填表时脑子里要有这一列）

| 列 | 语义 | 为什么不能省 |
|---|---|---|
| 状态码分布 | 有多少请求**被拒** | 决定「多少用户看到错误」 |
| 错误率 | 被拒 ÷ 总数 | 一行数字，方便对比 |
| **首帧 p50 / p95** | 用户多久看到**第一个字** | 📎 流式体验的主指标；⚠️ 平均值会骗人 |
| 总时长 p95 | 整段回答多久说完 | 受**上游预算**支配，不是我们慢不慢 |
| 墙钟 | 这一档整轮耗时 | 用它反算吞吐：`并发 ÷ 墙钟` |
| **池峰值** | DB 池最多借出几条 | 📎 **找瓶颈**：谁先到顶谁就是瓶颈 |

## 3. 判定（每条都要能失败）

| # | 判据 | 本次结果 | 不通过说明什么 |
|---|---|---|---|
| 1 | `并发 ≤ 闸门` 必须**全部 200** | | 闸门算错了 / 有别的旋钮在拒人 |
| 2 | `并发 ≥ 4 × 闸门` 必须**出现 503** | | 闸门没生效，或排队超时放得太宽 |
| 3 | 首帧 **p95 ≤ 目标 SLO**（如 1s） | | 容量到了但体验已经不行 —— 📎 这就是「零错误 ≠ 健康」 |

> ⚠️ **判据 3 是这份表单相对 13f 新增的**：只跑 1、2 会得出「8 并发全 200，很健康」的错误结论。

---

## 4. 结论（三句话，缺一不可）

1. **容量上限** = 不产生 503 的最大并发 = ______（推导：`slots + 吞吐 × queue_timeout`）
2. **绑瓶颈的是谁** = ______（📎 看池峰值：远低于上限 → 闸门先到顶 → 调池参数无意义）
3. **下次该动哪个旋钮 + 预期方向** = ______（例：把 `queue_timeout` 调大 → 错误率降但 p95 升）

## 5. 陷阱自查（每次压测逐条勾）

- [ ] `RATE_LIMIT_*` 已放大（否则测到的是限流器）
- [ ] 打的是**假上游**，没花真钱
- [ ] 每档 **≥ 3 轮**（p95 才有意义）
- [ ] 探针的**连接池 ≥ 并发**（否则测到的是客户端排队）
- [ ] 池占用的**采样窗口覆盖整轮**（📎 13f 的窗口只有 0.8s，c=32 一轮 1.8s → 峰值是**下界**）
- [ ] 同时记录了**错误率与 p95**（只看一个必然误判）
- [ ] 前置条件里每一项都填了（尤其「上游服务时长」）

## 6. 样本（本项目第一次，13f / 2026-11-20）

**§1 前置条件**：单进程 docker、`slots=4`、`queue_timeout=1.0s`、
上游 = 假上游 `12 帧 × 20ms`（≈0.41s/请求）、限流放大到 `60000/min`、
DB = SQLite 文件、探针 `--rounds 3 --gate 4`。

**§2 数据**

| 并发 | 状态码分布 | 错误率 | 首帧 p50 | 首帧 p95 | 总时长 p95 | 墙钟 | 池峰值 |
|---|---|---|---|---|---|---|---|
| 1 | 200 × 3 | 0% | **19 ms** | 27 ms | 410 ms | 0.41 s | 1 |
| 4 | 200 × 12 | 0% | **47 ms** | 72 ms | 436 ms | 0.44 s | **4** |
| 8 | 200 × 24 | 0% | **398 ms** | 504 ms | 871 ms | 0.87 s | **4** |
| 16 | 200 × 36 + 503 × 12 | 25% | 463 ms | 884 ms | 1258 ms | 1.26 s | **4** |
| 32 | 200 × 44 + 503 × 52 | 54% | 761 ms | **1485 ms** | 1788 ms | 1.79 s | **4** |

**§3 判定**：① 通过（c=1/4 全 200）② 通过（c=16/32 出现 503）
③ **不通过** —— c=8 已到 398ms，离 1s SLO 只剩 2.5 倍余量。

**§4 结论**

1. 容量上限 ≈ **14**（`4 + 10 × 1.0`，吞吐 10 req/s、服务 0.41s）
2. 绑瓶颈的是**上游闸门**（池峰值恒 4，上限 15）→ 调池参数无用
3. 要提高容量，动 `slots`（但会放大上游压力），**不要**动池
